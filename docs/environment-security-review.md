# Environment changes: execution boundary review

This review covers the configuration-execution and editor-write changes required by CONTRIBUTING.md. Docker checks and platform-native acceptance are separate verification gates; this review does not replace them.

Preparation previews read configuration, discovery, lock metadata and receipts without resolving online metadata, decrypting profiles or launching tasks. Execution requires an interactive confirmation or explicit `--yes`. Resume binds to a canonical project directory and input fingerprint, revalidates completed steps and refuses changed selections. SDK downloads continue through existing integrity, ownership, platform and install-lock checks. Python environment creation refuses unowned directories. Project tasks require an explicit declared task name and keep the normal task/profile resolver semantics.

Background editor context does not decrypt environments or execute project code. Explicit environment checking retains trust/identity/contract enforcement and zeroizes decrypted values. Portable reports exclude machine paths, local fingerprints, command arguments and variable values. Managed runtime probes suppress startup hooks and cap duration and output. Venv identity distinguishes its invocation path from a symlinked base interpreter. Native debug probes launch a nonce-scoped, controlled program with an explicit empty dotenv file and collect only executable/version observations. This proves that launch, not arbitrary project debug/test configurations.

Editor binding requires Workspace Trust and a field-level before/after preview. The extension rechecks project context and existing values before writing, scopes values to the selected workspace folder and current extension host, records its ownership before applying, and restores only unchanged owned values. Later user edits are retained. Setup locks are independent from nested install/config locks, avoiding self-deadlock. Journal and report destinations reject symlinks/non-regular files; JSON reads are size bounded.

Security regressions include read-only preview, changed-input resume refusal, portable report redaction, disabled startup hooks, bounded subprocess termination, venv/base-interpreter distinction and protocol compatibility. Existing trust, encrypted-variable, owner-receipt, task, shim and installer suites remain required. User-selected project tasks retain their normal process permissions; preparation does not claim to sandbox them.

The 2.14 compatibility readers limit files to regular files of at most 1 MiB within the canonical project, do not evaluate Gradle/Python/JavaScript code, and keep unsupported declarations unknown. Individual rule overrides cannot disable integrity, ownership or trust. Setup checks known conflicts both in its preview and again before installation after first-time metadata resolution.

Team reports whitelist variable contract metadata and compare SDK content identities, never secret-derived hashes. Report inputs reject unsupported schemas and duplicate runtime identities. Source probes retain configured source ordering and automatic official fallback, use bounded requests, and omit raw error chains and private URLs. Enterprise CAs augment normal roots without disabling certificate or hostname validation. Loopback acceptance verifies rejection of an untrusted certificate and success with the explicitly configured CA, with external fallback blocked by a local dead proxy.

Offline delivery includes all requested target artifacts and overlays; portable Bun x64 requires both CPU variants. Bundle import validates the complete manifest/lock/content set before cache writes, with entry/count/expanded-size limits. Tests exercise valid import, missing entries, empty manifests, extra files and modified bytes. Project package caches, platform installations and application effects remain outside SDK delivery guarantees.
