# Encrypted dotenv and identity-storage review

Scope: the Pinset 2.16 environment-profile format, local identity storage, CI onboarding, recipient changes, and minimum downloadable release. This is an implementation-boundary review, not an external security audit or a release claim.

- New profiles are UTF-8 `.env.<profile>` files with visible validated variable names. Each value is a separate age X25519 payload encoded as `encrypted:pinset:v1:<base64>`. Profile parsing is size bounded, rejects duplicate names that differ only by ASCII case, and rejects plaintext or malformed encrypted assignments.
- Setting, importing, or removing a value uses only the public recipients stored in `pinset.toml`. A targeted update does not decrypt unrelated values and preserves their ciphertext. Reading, checking, revealing, exporting, executing, and changing recipients require an authorized private identity.
- Newly generated local private identities are written directly to the operating-system credential store. Identity metadata contains only the public recipient, local identifier, and backend. Pinset 2.16 does not create private-key, recovery, `.env.keys`, or temporary plaintext files, and it no longer loads `PINSET_IDENTITY_FILE` at runtime.
- `pinset env access request` creates a credential-store identity and prints only its public request code. The CI variant requires an interactive terminal, prints the new private identity once for immediate transfer to a platform secret manager, and does not save it locally. Command output and shell history remain the operator's responsibility.
- Granting or revoking access decrypts in memory and re-encrypts every value for the resulting recipient set. Existing project trust fingerprints detect policy or profile-path changes. Removing the final usable recipient or losing all credential-store and CI identities makes ciphertext unrecoverable; there is deliberately no Pinset recovery-key file.
- Profile reads require the encrypted dotenv header and independently parseable age payloads. Whole-file `.age` profiles have no compatibility reader or migration command and fail closed as invalid profiles.
- Decrypted values are zeroized where the existing environment boundary permits and identity environment variables are removed before launching the business process. This reduces accidental forwarding but is not process isolation: an authorized program receives the plaintext environment and retains the invoking user's filesystem and network permissions.

Local regression coverage includes per-value ciphertext isolation, public-recipient-only writes, CLI set/list behavior without an identity, device grant/revoke, whole-file age rejection, parser contracts that reject removed compatibility options, and the encrypted-environment execution and trust suites. Installers, the Action, and self-update reject versions below 2.16.0. The published-release verification workflow removes assets from older Releases only after all 2.16.0 native verification jobs pass; release notes and Git tags remain. Native OS credential-store acceptance, CI platform secret transfer, and actual publication remain separate gates.
